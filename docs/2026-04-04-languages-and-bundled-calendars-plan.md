# План: дополнительные языки и предзагруженные календари

Документ фиксирует **цель доработки**, **полный перечень работ** и **пошаговый план** внедрения. Реализацию удобно вести по фазам: сначала расширение локализации интерфейса, затем несколько встроенных JSON-календарей и правило их смены при смене языка.

## Цель

- Добавить в приложение **несколько языков интерфейса** (сейчас поддерживаются только `ru` и `en` в `src/shared/lib/i18n`).
- Добавить **несколько предзагруженных (bundled) производственных календарей** на год: использовать `calendar2026.json` (RU / дефолт), `calendar2026TR.json`, `calendar2026IDN.json`, `calendar2026JP.json` из корня репозитория (**реализовано:** `require` в `src/entities/calendar/model/bundledCalendarJsonByLanguage.ts`, сид в `seedBundledYearIfNeeded` по языку из `getStoredLanguage() ?? detectDeviceLanguage()`).
- Включить в продукт **языки интерфейса и производственные календари** для **Турции**, **Индонезии** и **Японии** (см. таблицу ниже) — помимо уже запланированных `ru` / `en`.
- **По языку (локали) устройства** при подходящих условиях **автоматически выбирать и язык приложения, и bundled-календарь** одной и той же логикой маппинга (первый запуск / сидирование пустой БД и согласованное поведение с сохранёнными настройками — см. раздел «Системный язык устройства»).
- При смене языка интерфейса **вручную в настройках** **автоматически подставлять календарь, соответствующий языку/региону**, с **исключением для английского**: при выборе английского языка **не** выполнять автоматическую замену активного года в SQLite на «английский» bundled-календарь (сохранить текущие данные пользователя; подробнее — в разделе «Правило смены календаря»).

## Целевые регионы: язык UI и bundled-календарь

Один код `AppLanguage` связывает **перевод интерфейса** и **предзагруженный производственный календарь** страны (грид дней, праздники, сокращённые дни — по данным для соответствующей юрисдикции).

| Регион | Код языка приложения (`AppLanguage`) | Типичные префиксы системной локали | Bundled JSON (файлы в репозитории) |
|--------|--------------------------------------|-------------------------------------|-------------------------------------|
| Россия (уже есть) | `ru` | `ru` | `calendar2026.json` |
| Международный / fallback | `en` | `en`, прочие нераспознанные | тот же `calendar2026.json` как дефолт при сидировании (см. правило для `en` при смене языка) |
| Турция | `tr` | `tr`, `tr-TR` | `calendar2026TR.json` |
| Индонезия | `id` | `id`, `id-ID` | `calendar2026IDN.json` |
| Япония | `ja` | `ja`, `ja-JP` | `calendar2026JP.json` |

**Используемые bundled-файлы на 2026 год:** `calendar2026.json` (RU / дефолт), `calendar2026TR.json`, `calendar2026IDN.json`, `calendar2026JP.json` — они лежат в корне репозитория и проходят тот же путь валидации, что и импорт. Важно сохранить **1:1** между кодом языка UI и выбором bundled при авто-логике.

## Системный язык устройства

**Требование:** по **языку/локали устройства** (`Intl.DateTimeFormat().resolvedOptions().locale` или эквивалент в React Native) автоматически выставляются **язык интерфейса** и **какой bundled-календарь считать стартовым** (при создании БД с нуля).

Рекомендуемая логика (уточнить при реализации):

1. **Первый запуск**, в настройках ещё **нет** сохранённого языка пользователя: вычислить `AppLanguage` из системной локали (маппинг `tr*` → `tr`, `id*` → `id`, `ja*` → `ja`, `ru*` → `ru`, остальное → `en` или договорённый fallback). Одновременно при `seedBundledYearIfNeeded` подставить **тот же** региональный bundled для этого языка (для `en` — политика дефолтного календаря как в фазе 2).
2. **Язык уже сохранён пользователем** в SQLite/AsyncStorage: при старте приложения **не перетирать** его системной локалью без явного действия (опционально: пункт «Как в системе» в настройках — отдельная задача).
3. Смена **системного** языка в ОС **во время работы** приложения: либо не отслеживать до следующего cold start, либо слушать событие и предлагать перезапуск — зафиксировать выбранный вариант в отчёте по реализации.

Таким образом «автоматически с языка устройства» относится к **согласованному старту**: и UI, и календарь приходят из одного маппинга локали → `AppLanguage` → bundled.

## Текущее состояние (отправная точка)

- Тип `AppLanguage` и словари месяцев/дней недели: `src/shared/lib/i18n/index.ts`.
- Автоопределение языка устройства: `detectDeviceLanguage` / `mapLocaleStringToAppLanguage` (`ru` / `tr` / `id` / `ja` / иначе `en`, с `try/catch`).
- Переключатель в настройках: `src/shared/ui/LanguageSwitch.tsx` — опции из `AGREED_APP_LANGUAGE_CODES`, вертикальный список; в списке — нативные автонимы (`getLanguageNativeLabel`); в подзаголовке строки и в «О приложении» для **текущего** языка — `getLanguageLabel` относительно UI (`SettingsScreen`).
- Сохранение языка: `src/shared/lib/settings/repository.ts`, контекст `LocalizationProvider`.
- Каноническое хранилище года — **SQLite**; при пустой/битой БД сид через `seedBundledYearIfNeeded` из bundled, выбранного по `getStoredLanguage() ?? detectDeviceLanguage()` и реестру в `bundledCalendarJsonByLanguage.ts` (см. таблицу регионов в этом документе).

## Правило смены календаря (уточнение требования)

**Вариант A (рекомендуемый для продукта):**  
- Языки **кроме `en`**: при смене интерфейса на такой язык, если для него есть bundled-календарь на **тот же активный год**, выполнить **replace** в SQLite (как при импорте), **без** дополнительного диалога — это осознанный выбор «я смотрю календарь региона X».  
- Язык **`en`**: смена только UI; **активный календарь в SQLite не трогаем** (не перезаписываем bundled «US/UK» и не откатываем к дефолту), чтобы не ломать сценарий «импортировал свой JSON → переключил на английский для интерфейса».

**Вариант B (если позже решите иначе):**  
Для `en` тоже привязать конкретный bundled-календарь — тогда явно описать, какой регион (например US vs UK) и нужен ли диалог подтверждения.

В коде и тестах зафиксировать выбранный вариант; в этом документе дальше идёт план под **вариант A**.

6. **Конфликт с пользовательским импортом** — **выполнено (2026-04-04)**  
   - **Решение:** флаг в SQLite (`app_metadata`, ключ `active_calendar_user_json_import`): выставляется при `replaceActiveYear(..., 'user_json_import')` из потока импорта JSON; сбрасывается при любой замене из bundled (`replaceActiveYear(..., 'bundled')`, в т.ч. сидирование).

   - В настройках под блоком языка показывается короткая подсказка `settings.rows.language.userImportHint`, если активный год пришёл из импорта.

7. **Названия праздников в данных** — **выполнено (2026-04-04)**

## Риски и вопросы на согласование

- **Потеря пользовательского импорта** при переключении языка (если не ввести флаг или подтверждение).  
- **Размер APK**: несколько полных годовых JSON увеличивают бандл.  
- **Юридика данных**: производственные календари разных стран — разные источники; имеет смысл указать в «О приложении» регион по умолчанию для каждого bundled.
