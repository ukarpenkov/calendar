## Фича: Обновление bundled-календаря на 2027 год

Перевести приложение с предзагруженного производственного года **2026** на **2027** по всем регионам (RU / TR / ID / JA). После релиза в шапке экрана года должно быть «Год 2027» / «Year 2027», а праздники, переносы и предпраздничные дни — по **утверждённым** официальным источникам каждой страны.

**Ветка:** `feat/calendar-2027`  
(как остальные фичи: `feat/vacation`, `feat/widget3`, …)

**Не високосный год:** 2027 = **365** дней. Тесты на длину года можно оставить `toHaveLength(365)`.

---

### Зачем это не «просто поменять цифру»

Шапка года **уже берёт год из данных**, не из хардкода:

```165:165:src/pages/year/ui/YearHomeScreen.tsx
          {t('year.home.title', { year: calendar.year })}
```

Как только активный календарь станет 2027, заголовок сам станет «Год 2027». Но:

1. Bundled JSON в корне репозитория сейчас все на `year: 2026`.
2. Константа `BUNDLED_CALENDAR_YEAR = 2026`.
3. Сид SQLite **не перезаписывает** уже сохранённый полный год. У пользователя с установленным 2026 после обновления APK шапка останется «Год 2026», пока не сделаем миграцию.
4. Картинки праздников завязаны на ключ `дата|название` — без новых ключей на 2027 праздники уйдут в fallback.
5. В настройках и подсказках импорта год **захардкожен** строкой «2026».

**Экран года.** Менять разметку шапки не нужно: `year.home.title` = `Год {{year}}` / `Year {{year}}` / `{{year}} yılı` / `Tahun {{year}}` / `{{year}}年`. Источник — `calendar.year`.

После миграции на 2027 в ноябре–декабре **2026** карточка **не** покажется (годы не совпадут) — это нормально: 2027 уже в приложении, звать в Telegram за JSON не нужно. В ноябре 2027 карточка снова появится уже про 2028.

После смены данных в настройках строка «Активный год» (`settings.rows.activeYear.subtitle` с `{{year}}`) подтянется сама.

### 3. Bundled JSON — 4 файла, тот же контракт

Сейчас в корне:

- `calendar2026.json` — RU (+ UI `en`)
- `calendar2026TR.json`
- `calendar2026IDN.json`
- `calendar2026JP.json`

**Сделать:** новые `calendar2027.json`, `calendar2027TR.json`, `calendar2027IDN.json`, `calendar2027JP.json`. Старые 2026 из бандла убрать (тест/Metro больше не `require` их). Схема без изменений:

```json
{
  "year": 2027,
  "holidays": [{ "date": "2027-01-01", "name_ru": "...", "name_en": "...", "name_tr|id|ja": "..." }],
  "weekends": ["2027-01-02", "..."],
  "preholidays": ["2027-04-30"]
}
```

Правила импорта (уже в коде):

- `weekends` — **только** субботы и воскресенья. Перенос на будний день → в `holidays`, не в `weekends`.
- Если суббота стала рабочим днём (компенсация) — этой даты **нет** в `weekends`.
- `preholidays` не пересекаются с holidays/weekends (иначе импорт их выкинет).
- Для TR/ID/JA заполнять локальное имя (`name_tr` / `name_id` / `name_ja`), как в текущих файлах.
- Имена праздников по возможности **те же формулировки**, что в 2026 (от них зависят ключи картинок).

Прописать имена файлов здесь:

- `src/shared/config/agreedLanguagesAndBundledCalendars.ts` → `BUNDLED_CALENDAR_YEAR = 2027` и `BUNDLED_CALENDAR_JSON_FILENAME_BY_*`
- `src/entities/calendar/model/bundledCalendarJsonByLanguage.ts` → `require('../../../../calendar2027….json')`

### 6. Миграция SQLite для тех, у кого уже стоит 2026

Сейчас `seedBundledYearIfNeeded`: если в БД полный активный год — **вернуть его и выйти**. Обновление APK само по себе 2027 не подставит.

**Нужно:** если источник `bundled` и активный год **не** `BUNDLED_CALENDAR_YEAR` (т.е. старый 2026) — `replaceActiveYear` текущим bundled JSON **того же региона** (`resolveBundledCalendarRegionForSeed` / сохранённый регион).

Не трогать, если `active_calendar_source === 'user_json_import'` (пользователь сам залил JSON).

Где править: `src/entities/calendar/model/repository.ts` (`seedBundledYearIfNeeded`). Тесты: `__tests__/calendarRepository.test.ts`.

**Отпуска:** периоды в своей таблице, без привязки к году. После смены на 2027 отпуска за 2026 на сетке не видны (даты не из этого года). Решение: оставить как есть **или** при bundled-миграции удалить периоды вне 2027. Зафиксировать до реализации; проще оставить.
